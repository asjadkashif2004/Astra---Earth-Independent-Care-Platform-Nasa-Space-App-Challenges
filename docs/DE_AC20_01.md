## Requirement and reason for the exception

The original requirement remains exactly:

> 3D judge-performance mode sustains ≥30 FPS on the team's designated minimum machine.

Source: [master research AC-20](../research/ASTRA_Deep_Research.md), Definition of Done. Related module contracts and performance budgets specify a60FPS desktop target,≥30FPS judge mode, a recent8GB/WebGL2 judge browser, and a quality-reduced profile using fewer particles/shadows/postprocessing. The research does not assign AC-20 to N03 or specify an exact CPU/GPU, trial duration or external certifier.

## Approved provisional measurement protocol

The user approved **three warmed60-second trials at1920×1080**, subject to identifying the designated minimum judge hardware. This is the provisional verification protocol, not an executed result or a replacement for the original criterion.

1. Identify the device/configuration and label it either a named reference machine or the explicitly designated minimum judge machine. Before designation, component measurements on reference hardware are provisional and cannot close AC-20.
2. Record browser/OS/GPU/driver, physical viewport1920×1080, actual DPR/browser zoom, quality tier/render scale, asset/model versions, host placement, demo load, power/thermal conditions, warm-up duration and measurement tool. Measure cold loading separately; do not hide it inside warm results.
3. For each relevant scene/mode, run three warmed60-second trials with genuine active3D animation or camera movement and live six-crew telemetry. Exercise stage-relevant interaction and record the workload. The standard research demo is approximately60 scalar events/s. Quality gating must never invent medical motion to keep the benchmark active.
4. Target60FPS in standard desktop graphics. In the quality-reduced performance profile require at least30 measured presentedFPS in each recorded one-second active interval. Preserve per-second results, frame-time distributions, stalls/dropped frames and raw supporting traces. This is the approved provisional operationalization of sustained performance, not wording added to the research. A run-wide average alone is insufficient.
5. Measure real visible-browser frame presentation with a suitable trace/tool and disclose its limitations. Draw submissions, requestAnimationFrame cadence, shader timings and headless results are useful diagnostics and must be labeled separately; none alone establishes presentedFPS. If presentation evidence is unavailable, do not certify AC-20.
6. Keep **quality-reduced performance mode** independent of **reduced motion**. Performance mode lowers rendering cost while retaining active animation; reduced motion may intentionally be static or event-driven. Test reduced motion, quality/stale freezes, no-WebGL and2D/text fallback as separate usability/correctness cases. They do not replace the active3D FPS workload.
7. Recheck warm interactive shell≤3s, simple API p95<200ms and telemetry-to-UI p95<500ms under the scene's demo load. Distinguish mounted DOM, usable controls, metric DOM updates and visible paint in the results. Backend scalar≥100 observations/s and detector<50ms/batch budgets remain unchanged; integration measurement does not authorize backend redesign.
8. Preserve responsive/accessibility and N01/N02 safeguards: four required viewports,200% zoom, keyboard/focus, actual monitoring/Gray status, source ownership/provenance/privacy, alerts, human acknowledgement and Earth reception separation. Record one owned loop per active scene, disposal after repeated navigation, transferred asset bytes and decoded CPU/GPU memory separately. Never downsample medical data or suppress warnings to obtain a graphics pass.

All targets and any tool/hardware limitations must be visible in the owning module's completion report. A materially changed protocol requires an explicit recorded decision; do not silently relax duration, workload, resolution or the30FPS minimum.
