## Filesystem, process and WAL isolation

Readers run through the existing Bubblewrap and Python3 tools, with the installed Node executable bound read-only as `/runtime/node`; no package/runtime download is needed. Private mount/PID/network/IPC/user namespaces, dropped capabilities, cleared environment, read-only runtime/code binds and a private proc/dev view exclude project databases, home, credentials and application directories. A source directory fd is mounted with supported `--ro-bind-fd`; the wrapper closes inherited directory capabilities before Node starts, preventing a writable-directory-fd bypass. Only the builder/writer gets a writable fixture mount. The host path cannot be selected through the CLI. This Linux implementation is not a cross-platform or hostile-host security certificate.

Each child checks no application/home exposure, no external routes and a write-denied root before SQLite use. Readers additionally prove directory creation and database O_RDWR are denied by the read-only mount. SQL read-only mode alone is never treated as filesystem proof. Source-byte/inventory snapshots are taken before opening and after closing the reader connection. All writer-side hashing occurs in the supervisor, which holds no SQLite connection: opening and closing a second database fd in a SQLite-owning process can invalidate its POSIX lock assumptions. The writer must actually create sidecars before announcing WAL readiness.

Controlled WAL tests distinguish quiescent reader hash invariance, a reader's old committed snapshot during a writer commit, later visibility of the new generation and checkpoint blocking/release. Missing WAL/SHM, exclusive-lock BUSY and missing database fail closed rather than changing permissions or creating/recovering files. Derived missing-sidecar copies are test fixtures only; copying live operational SQLite files is not authorized or qualified.

## Durability, budgets and cancellation

Public single-call executions and the four-call CLI workflow use the existing fsynced/atomic N16 execution ledger under a new scratch `traces` directory. Trusted caller/source-instance/manifest context, validated arguments, start/result/end or failure/cancellation are persisted outside SQLite. Completion requires durable result/checkpoint; persistence failure withholds success. Unauthorized preexecution requests do not open a source or start a reader. Negative harness runs are labeled controls, not successful data retrieval. Cold recovery checks committed hashes without rerunning SQL.

The frozen limits are1MiB DB/4MiB WAL,64MiB monitored scratch/output,512MiB connector RSS,1s read supervision,10s workflow/writer bound,250ms read-transaction target and250ms termination escalation. Native launch/exit time and monitor-flush time are recorded separately. A child-side timer bounds the intentional held-transaction control; a parent watchdog covers stalled processes and aborts. Only owned process groups are signalled, with birth-checked PID sampling/cleanup verification and no remaining observer queue. Uninterruptible kernel IO cannot be guaranteed away; failure to confirm cleanup is a failure, never success.

Durable incremental resource journals record source phases, owned-process VmHWM and counted storage. Final inventory verifies retained roots.
