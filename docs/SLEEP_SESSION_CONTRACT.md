# Completed sleep session contract — 2026-10-23

This is the explicitly approved Last Sleep lifecycle repair, not a new monitoring or forecasting module. N01 ordering/ownership/privacy and N02 detector thresholds, quality gates and acknowledgement requirements remain in force. See [completion and verification](SLEEP_LIFECYCLE_COMPLETION.md), [N01](N01_COMPLETION.md) and [N02](N02_CONTRACTS.md).

## Records and updates

SQLite schema version 3 adds the append-only `sleep_sessions` ledger. Each `astra.sleep-session.v1` row contains `record_id`, stable `session_id`, `crew_id`, integer `revision`, `supersedes_record_id`, UTC `start_at`, `end_at`, `scheduled_end_at`, `duration_hours`, source observation/receipt/knowledge times, source, quality, synthetic provenance, correction reason, historical-fixture flag and the full canonical observation. Update/delete triggers protect prior revisions. Scalar/snapshot pruning does not delete this ledger.

`astra.telemetry.v1` retains its existing required fields and optionally accepts `sleep_session` for `sleep_duration` only. Its allowed fields are `session_id`, `revision`, `start_at`, `end_at`, optional `scheduled_end_at`, `reason`, `historical_fixture`. IDs start `SLEEP-`; revisions are sequential, 1–100000. Completed-session sources declare one observation per day (`sampling_hz: 1/86400`). A finite duration must match `(end_at-start_at)` in hours, within the existing 0–24 h plausibility range; the interval must be positive and end no later than the observation. Missing quality requires a null metric value. Existing UTC validation, 24-hour observation-ingestion bounds, import-device ownership and strictly increasing imported observation timestamps remain unchanged. Unknown fields still reject with 422; conflicts reject atomically with 409.

The first record is revision 1. A correction appends the same session ID at exactly the next revision, from the same crew/source/device, with a nonempty reason and a strictly newer observation time. It does not overwrite the original row or any queued/received snapshot. Only the current session may be corrected in this bounded repair. New imported sessions from the same producer must advance completion time. Server-side simulator corrections use the trusted `Engine.correctSleep(crewId, sessionId, {expected_revision, start_at?, end_at?, reason, quality?})` boundary. It has no public write route. Imported corrections use the existing credential-protected telemetry ingestion route; no credential is added or exposed by this repair.

Completion/correction, raw observation (when current), source ownership, derived readings/detection, snapshot, audit, delayed queue and checkpoint use the existing transaction. Failure restores SQLite, in-memory state and the communications cursor. Stable held records produce no new scalar insert, observation ID, source timestamp, quality transition or N02 persistence sample. Intermediate completions caught up during a step are recorded in the ledger, not replayed as fabricated live detector observations.

## Synthetic schedule and reproducibility

`completed-sleep-v1` assumes one completed session per mission day at **07:00 UTC**. This is an illustrative synthetic schedule, not measured crew sleep or a medical recommendation. A SHA-256 key uses generator version, seed, crew, scheduled completion and scenario to derive the session ID and small deterministic variation around the existing synthetic personal baseline. CREW-03's sleep-debt and sleep-fatigue scenarios apply their illustrative 2.6/3.1-baseline-scale reductions once to future completed sessions. They never rewrite the previous night. Current non-sleep scenario signals remain unchanged.

An existing record is returned unchanged until another scheduled completion, even if the seed or scenario changes. A correction preserves the original schedule anchor for the next completion. Catch-up is bounded to at most 365 completed slots per producer call; normal telemetry ingestion/cadence constraints still apply. Pure generator callers must pass the previous per-crew records as `sleepSessions` to retain context across scenario/seed transitions; Engine persists and supplies them automatically.

On a new database or an old simulator checkpoint without session metadata, the first completed record is explicitly a **synthetic historical fixture**. Its value comes from the deterministic session generator, not from freezing the last random scalar. Existing historical snapshots and scalar imports are not rewritten or invented into completed sessions. Existing seed-history snapshots are still explicitly synthetic fixtures. A scalar-only imported sleep channel retains ownership/value/time/quality and is presented as **Sleep observation — session unverified** until its authorized producer supplies actual session metadata.

## Time, freshness and reception

`end_at` is session completion; observation `ts` is source observation/correction time; `received_ts` is source/gateway receipt. Server-owned ingestion records distinguish `mission_received_at` and real host receipt. Ledger `known_at` is the mission ingestion time. A catch-up record more than one day old is marked historical and observed at catch-up time to respect the existing ingestion-age bound; its old completion time remains visible and governs freshness. Reproducibility includes values, IDs and mission/source times, not wall-clock host receipt or random application run IDs.

Freshness derives from the earlier of observation time and completion time using the unchanged N01 rule `max(5 seconds, three source sampling periods)`. Thus a daily sleep observation normally stays current for three mission days; a newly reported correction to an old session cannot rejuvenate it. Missing/suspect/low-confidence/artifact observations remain unavailable/Gray under existing aggregate and per-channel gates. Other recovering sensors do not repair a missing sleep record; a valid source correction or new completed observation is required.

Earth still displays only immutable delivered snapshots, with original observation/transmission/reception times. Onboard correction never edits queued or received packet contents. `GET /v1/crew/{id}/sleep-sessions?limit=180&before=<UTC time>` uses existing authenticated telemetry-read permissions and astronaut self scope. `before` filters **known_at**, not completion time, and invalid cutoffs reject with 422. This is an onboard record API, not a new Earth-delivery API. Earth consumers must retain their delivered-packet boundary and, for retrospective ledger queries, constrain `before` to that delivered packet's `observed_at`; no Earth frontend ledger fetch is added. A historical completion cannot be exposed just because its end predates reception.

## Consumers and limits

Overview and Crew Health read the same authoritative projected metric. Completed time/revision/source are exposed in the metric detail/Overview tooltip. Replay uses stored values and metadata; old scalar-only frames are labeled unverified. Typed sleep charts deduplicate stable observations and render completion/correction points with steps, never fake continuously varying sleep samples. The service-worker shell version changes to deliver these consumer updates.

The continuous `linear-trend-v2` sleep forecast and its old calibration are incompatible with discrete sessions. Sleep forecasting returns `available: false` and `unsupported_component: 'sleep_duration'`; no new sleep prediction is persisted. Historical predictions/calibration artifacts remain unchanged. HR/HRV forecasting is unchanged. Calibration tooling excludes sleep from future runs; tools now declare their actual simulated sampling cadence. Neither tool was run or recalibrated for this repair.

No N02 rule, threshold, persistence window or acknowledgement safeguard changes. A repeatedly held low sleep value cannot acquire false single-signal persistence; sparse-session-specific inference remains future separately approved work. The existing seeded baseline is a synthetic statistical prior, not a dated 30-day session archive. Sleep stages, individual schedules, cumulative deficit models, old-session correction UI/API, scientific validation and broad forecasting remain outside this repair.
